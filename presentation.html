Tooling Foundation

Guardrails exist before the codebase grows. Retrofitting is painful.

Principle: The first commit sets the standard every subsequent commit inherits.

The Empty application/ Layer Decision

Deliberate omission: With a single domain and Next.js API routes already acting as the driving adapter, an application/ layer would be pure boilerplate. If cross-domain orchestration were needed, this is where it would go.

Domain Model & Business Rules

The Candidate aggregate enforces its own invariants. Route handlers contain zero business logic.

State Machine

NEW
→ shortlist(reason) →
SHORTLISTED
NEW
→ reject(reason) →
REJECTED

Terminal states: SHORTLISTED and REJECTED are terminal. No transitions allowed from either. canTransition(status) returns status === 'NEW'.

Candidate Aggregate Root

export class Candidate {
  public readonly id: string
  public readonly name: string
  private _status: CandidateStatus        // Encapsulated — no direct mutation
  private _reason: string | null
  private _decisionDate: Date | null

  private constructor(...) { }           // Cannot be instantiated directly

  static create(...): Candidate {       // Static factory — validates on creation
    if (!isValidName(name)) throw new ValidationError(...)
    return new Candidate(...)
  }

  shortlist(reason: string): void {
    if (!isValidReason(reason)) throw new ValidationError(...)
    if (!this.canTransitionTo('SHORTLISTED')) throw new InvalidTransitionError(...)
    this._status = 'SHORTLISTED'
    this._reason = reason
    this._decisionDate = new Date()
  }
}

Shared Validation Trade-off

A deliberate anti-pattern — single source of truth > theoretical purity at this scale.

The Solution

// domain/validation/rules.ts — pure functions, zero framework imports

export const MIN_REASON_LENGTH = 10

export function isValidName(name: unknown): boolean {
  return typeof name === 'string' && name.trim().length > 0
}

export function isValidReason(reason: unknown): boolean {
  return typeof reason === 'string' && reason.trim().length >= MIN_REASON_LENGTH
}

export function canTransition(status: CandidateStatus): boolean {
  return status === 'NEW'
}

Shared vs Separated

Shared
3 pure predicates + 1 constant
isValidName, isValidReason, canTransition
Backend Only
Error → HTTP status mapping
ValidationError → 400
InvalidTransitionError → 409
Frontend Only
Error display logic
Toasts, banners, ErrorBoundary

Trade-off: Coupling is limited to "what constitutes valid data" — 3 predicates and 1 constant. Error handling stays separated. At this scale, single source of truth > theoretical purity.

State Management & Optimistic UI

TanStack Query for server state. React 19 useOptimistic for instant feedback.

Before → After

Before: Raw fetch + useEffect

Manual fetch calls, manual re-fetch after mutations. No caching, no loading/error states, no retry.

After: TanStack Query v5

Automatic caching, loading/error states, retry, mutation + invalidation, type-safe query keys.

Optimistic Update Flow

// React 19's useOptimistic — updates UI before server responds

type OptimisticAction =
  | { type: 'add';    candidate: CandidateDTO }
  | { type: 'update'; id: string; status: CandidateStatus; ... }

function candidatesReducer(state, action) {
  switch (action.type) {
    case 'add':    return [...state, action.candidate]
    case 'update': return state.map(c =>
      c.id === action.id ? { ...c, status: action.status, ... } : c
    )
  }
}

Drag-and-Drop Decision Flow

1. User drags NEW card to SHORTLISTED column
2. Sheet opens with prefilled decision (SHORTLIST)
3. User enters reason (min 10 chars, validated inline)
4. On submit: addOptimistic({ type: 'update', ... }) — card moves immediately
5. submitDecision.mutateAsync(...) fires API call
6. await queryClient.invalidateQueries(...) reconciles with server truth
7. If server fails: TanStack Query refetches → optimistic state reverts automatically

Key Bug Fix: useTransition for Optimistic UI

Before (broken)
// Module-level — no component scope
import { startTransition } from 'react'

startTransition(async () => {
  addOptimistic({ type: 'update', ... })
  await mutateAsync(...)
  await invalidateQueries(...)
})
After (fixed)
// Component-scoped — coordinates with useOptimistic
const [isPending, startTransition] = useTransition()

startTransition(async () => {
  addOptimistic({ type: 'update', ... })
  await mutateAsync(...)
  await invalidateQueries(...)
})

Why: The module-level startTransition can't coordinate with useOptimistic's render scope — optimistic state never flushed instantly. The useTransition() hook provides a component-scoped version that does. Bonus: isPending flag for loading indicators.

Accessibility

WCAG 2.1 Level AA compliance. Drag-and-drop that works without a mouse.

Why this matters: Kanban boards are notoriously inaccessible — most rely entirely on mouse drag. By supporting keyboard DnD, screen reader announcements, and focus management, the board is usable by everyone including users with motor or visual impairments. Accessibility isn't a nice-to-have — it's a quality signal.

Key Accessibility Decisions

🎯
Drag Validation at Source

Terminal-state cards have disabled: true on the draggable. Users can't start a drag that will fail — no confusing rejection at the target.

⌨️
KeyboardSensor

@dnd-kit's KeyboardSensor enables full keyboard DnD navigation. Arrow keys move between columns, Enter/Space to pick up and drop.

📢
ARIA Live Regions

<div aria-live="polite" aria-atomic="true" class="sr-only"> announces drag state changes to screen readers.

🏷️
Semantic Markup

Columns use role="group" + aria-label. Cards have aria-roledescription="draggable candidate card". Loading state uses aria-busy.

Screen Reader Announcements

"Picked up Alice Johnson from NEW. Use arrow keys to move between columns."

// Drag end — successful
"Moved Alice Johnson to SHORTLISTED."

// Drag end — cancelled
"Dropped Alice Johnson. No change."

// Drag end — same column

Additional A11y Features

  • role="alert" on error banners, aria-busy on loading skeletons

Neon DB & Repository Pattern

Repository interface as a port. Two adapters. Zero config for development.

Port (Domain Layer)

export interface CandidateRepository {
  getAll(): Promise<Candidate[]>
  getById(id: string): Promise<Candidate | null>
  save(candidate: Candidate): Promise<void>
  nextId(): Promise<string>
  reset(): Promise<void>
}

Async everywhere: Even the in-memory adapter returns Promises. This means swapping adapters requires zero changes to calling code.

Adapter Selection — Factory Pattern

export function getRepository(): CandidateRepository {
  if (instance) return instance

  if (process.env.DATABASE_URL) {
    // Lazy require() — avoids loading Neon deps when running in-memory
    const { NeonCandidateRepository } = require('./neon-repository')
    instance = new NeonCandidateRepository()
  } else {
    instance = new InMemoryCandidateRepository()
  }
  return instance
}

Drizzle ORM Schema

export const candidates = pgTable('candidates', {
  id:           varchar('id', { length: 20 }).primaryKey(),
  name:         varchar('name', { length: 255 }).notNull(),
  status:       varchar('status', { length: 20 }).notNull().default('NEW'),
  reason:       text('reason'),
  decisionDate: timestamp('decision_date', { withTimezone: true }),
  createdAt:    timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),
})

Upsert Pattern (Save)

save() uses INSERT ... ON CONFLICT DO UPDATE (upsert). Same method for both create and update. No separate create/update logic needed in route handlers.

E2E Scenarios (Playwright)

  • Create candidate with valid name → appears in NEW column
  • Create candidate with empty name → shows validation error
  • Click NEW card → sheet opens, submit shortlist with reason
  • Click NEW card → sheet opens, submit reject with reason
  • Drag card to SHORTLISTED → sheet prefills, submit moves card
  • Drag card to REJECTED → sheet prefills, submit moves card
  • Click SHORTLISTED card → sheet shows read-only details
  • Verify board state is consistent after all operations

No data layer mocking in integration tests. The in-memory repository is fast enough to use directly. This catches real integration bugs that mocks would hide (e.g., the Neon nextId lexicographic ordering bug).

Learnings & Reflections

What went well, what I'd do differently, and takeaways.

What Went Well

✔️
Tooling First

Investing in Prettier + ESLint + strict TS + Husky upfront meant every subsequent PR was automatically consistent. Zero formatting debates.

✔️
TDD as Specification

Writing failing tests first turned vague requirements into exact, executable specs. When tests go green, you know the feature works — no manual verification needed.

✔️
Incremental PRs

7 focused PRs instead of one big bang. Each PR was reviewable, testable, and deployable. Smaller blast radius for each change.

✔️
Domain Model Encapsulation

Private constructor + static factory + transition methods = impossible to create invalid state. The compiler catches business rule violations.

✔️
Repository Pattern Payoff

Adding Neon adapter required zero changes to domain or route code. The interface abstraction paid for itself immediately.

✔️
Optimistic UI + Error Recovery

React 19 useOptimistic gave instant DnD feedback. The useTransition hook provides a component-scoped startTransition that coordinates with useOptimistic. Combined with awaited invalidateQueries, the UI stays consistent even on server failure.

What Could Be Improved

🛠️
c_id vs UUID

Kept the prototype's c_1, c_2 ID format. In production, UUIDs would be more appropriate for distributed systems and avoid the nextId() race condition.

🛠️
Migration System

Neon schema was created via direct SQL. A proper migration system (Drizzle Kit) would make schema evolution trackable and reversible.

🛠️
API Validation Layer

Route handlers do manual type checking. Zod schemas would give automatic parsing, type inference, and better error messages.

🛠️
Comprehensive E2E

8 scenarios cover the happy paths. Edge cases (concurrent edits, network failures, slow connections) need additional E2E coverage for production readiness.

Key Takeaways

1. Standards before code — the first commit shapes everything after it.
2. Failing tests are the best specification language.
3. Hexagonal doesn't mean heavy — adapt the pattern to the project scale.
4. Shared validation is a pragmatic trade-off, not a mistake, when acknowledged explicitly.
5. Optimistic UI requires careful state management — useTransition (not the module-level startTransition) + awaited invalidation prevents flicker.
6. Incremental delivery builds confidence — each PR is a checkpoint that works.
